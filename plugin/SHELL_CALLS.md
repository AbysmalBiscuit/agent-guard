# Shell-call collection

`scripts/shell_calls.py` records shell tool attempts and outcomes for analysis of agent write patterns. It runs as separate `PreToolUse` and `PostToolUse` commands for Claude Code and Codex, plus `PostToolUseFailure` for Claude Code, independently of agent-guard's checks and text-log level. It emits no permission decision and never executes the captured command. Claude's matcher includes both `Bash` and its native `PowerShell` tool; Codex's matcher also includes `exec_command`, `shell_command` and `shell`.

The default destination is `~/Nextcloud/agent-guard/shell-calls`. WSL uses `/mnt/c/Users/Lev/Nextcloud/agent-guard/shell-calls`, sharing the Windows Nextcloud client with the cost statusline. `AGENT_GUARD_SHELL_LOG_DIR` selects another destination. The default Nextcloud directory must already exist; an unavailable destination produces a diagnostic without blocking the tool.

Records are immutable UTF-8 JSON files under `<harness>/<session>/<machine>/`. Session and machine directory names retain readable identifiers and a hash so identifiers remain distinct on case-insensitive filesystems. Resuming a session adds records to the same directory. Different machines write separate files, including when they resume the same session. A temporary file is renamed into place after writing; consumers read `*.json` and ignore temporary files.

Schema version 2 records include the hook event name, unique event ID, UTC capture timestamp, harness, full session ID, available subagent and tool-call IDs, command, machine and OS, and the complete original hook payload. Available turn ID, prompt ID, model, permission mode and transcript path are exposed at the top level. Missing command, session, tool-call ID or working-directory fields are identified in `capture_notes`. Older records remain readable; their schema version is unchanged.

`capture_stage` is `attempted`, `result` or `failure`, corresponding to the event name. Count `attempted` records when measuring tool-call frequency. A pre-execution hook does not establish that a command ran, succeeded, or changed a file. A result means the harness emitted a result hook; it does not independently prove success. Failure events identify failures reported by the harness. Permission rejection and cancellation do not reliably produce outcome events, so an unmatched attempt has an unknown outcome.

`call_key` joins events using harness, machine, session, subagent and tool-call ID. It excludes the turn ID so completion in a later turn can join the original attempt. It is null without a session or tool-call ID. Repeated hook invocations remain separate events rather than overwriting evidence. The machine is part of the identity: records collected on another computer are not automatically paired.

`hook_cwd` is the hook payload's working directory. `requested_workdir` preserves a supplied tool `workdir` or `cwd` verbatim, including relative paths. The compatibility field `cwd` prefers that requested directory and otherwise uses `hook_cwd`; `cwd_source` names the source. `requested_shell` and its compatibility alias `shell` are populated only from a supplied shell field, with `shell_source` identifying where it appeared. These fields do not establish the resolved execution directory or interpreter. A Codex tool named `Bash` can contain PowerShell on Windows, and Codex hooks can omit the original `exec_command` workdir and shell arguments. `environment_hints` records only `SHELL`, `COMSPEC`, `MSYSTEM` and `WSL_DISTRO_NAME`; these describe the hook environment, not a confirmed interpreter for the recorded command.

For outcome events, `result` exposes the response's shape and any structured exit code, duration in milliseconds, error or interruption flag. Missing values remain null. The collector does not infer an exit code from output text or treat a result event as a successful exit. `PostToolUseFailure` sets `result.is_error` to true and retains the error message. The complete response remains in `payload.tool_response`; failure details remain in the original payload as well.

Commands and payloads, including tool responses, are stored as received without additional truncation or redaction. The harness may already truncate a response, and a Codex command completed through polling may expose only its final output chunk. This collection is not a complete terminal recording. The collector reads no transcripts and captures no general environment dump. Existing text logs are not imported because their shortened session IDs and interleaved input rows cannot establish reliable attribution.

Set `AGENT_GUARD_SHELL_LOG=0` to disable collection. `AGENT_GUARD_MACHINE_ID` overrides the default hostname plus OS flavor when machines otherwise share a name. These settings affect collection independently of the text log's `log` setting.

The plugin's hook files do not register the collector. To enable it, register `python3 <plugin root>/scripts/shell_calls.py --harness claude-code`, or the same command with `--harness codex`, for the events above. Reload or resume a harness that loaded its hook configuration before the registration.

Run the collector tests with `python3 plugin/tests/shell_calls.test.py` from the repository root. They exercise the stdin hook entry point, concurrent calls, resumed-session grouping, result pairing across turns, full command and response preservation, missing metadata, failure handling and filesystem-safe identifiers. Run them with native Windows Python as well when changing file handling.

Hook contracts are documented in [Claude Code's hook reference](https://code.claude.com/docs/en/hooks) and implemented in [Codex's hook schema](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/hooks/src/schema.rs) and [shell tool handler](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs). Recheck the installed Codex version's source before relying on fields that its hooks omit.
